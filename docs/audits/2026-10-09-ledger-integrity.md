# 财务系统可靠性巡检 — 2026-10-09

目标站点：`https://cf.hnchpower.cn`。代码仓库：`wangmiao033/cf.hnchpower.cn`。

## 覆盖范围

本轮重点检查：生产部署和自动化测试、运营费用/押金/人工费用的后台列表接口及前端分页、工资导入并发防重、全局权限策略、利润分析聚合方式及近期生产日志。代码库包含多个独立子系统，本轮不是全站全部页面的手工端到端验收。

## 已确认并修复（在本 PR）

1. **工资汇总分页计算错误**：`/api/operating-expenses/payroll-batches` 过去返回 `total=len(items)`，并对仅当前分页的工资批次做应发、个人代扣、个税、实发和状态统计。现改为完整过滤集合的 SQL 聚合，再分页明细。
2. **运营费用明细只读取首 500 条**：费用总览、分类账、工资和押金以前全部固定请求 `limit=500`，导致超过限制时金额统计不完整。现有前端分页聚合函数检查服务端总数、空页、重复 ID 和期间变动，失败则停止显示报表，不再安静少算。
3. **切换月份、分类时旧请求覆盖新数据**：使用请求序号，忽略过期异步结果；出错页面提供提示及重试按钮，避免之前缓存记录被误认为当前月份。
4. **工资重复录入竞态**：新增/修改同公司同月份工资批次时，在 PostgreSQL 使用事务级 advisory lock 对相同归属进行串行处理，再进行已有批次检查。避免两个标签页同时通过“先查后写”。保留原有 409 冲突逻辑。
5. **分页顺序不稳定**：费用、押金和工资列表增加唯一 ID 稳定排序，防止同一创建时间数据在跨页中重复/丢失。

## 验证方式

- 后端 SQLite 工资账本分页/筛选统计回归测试和 advisory lock 条件测试。
- 前端 Vitest 测试，覆盖跨多页汇总、重复记录/页数变化失败处理。
- 原有前后端测试及生产构建必须通过 CI，且在发布后确认 Vercel 生产实例 Ready 和 GitHub 健康检查通过。
- 无线上真实工资、费用、银行、合同数据的写入/删除/状态变更。

## 已发现但本轮未修改的风险/后续事项

- **利润分析读全表**：`build_profit_analysis()` 会载入全部渠道、研发账单和经营费用，在数据规模显著增长后可能增加加载时间。建议后续做按月份 SQL 预聚合/缓存，并与现有 12 个月利润口径对账。
- **生产运行日志**：Vercel 当前套餐最近运行日志保留窗口较短，无法用近期日志推断较久之前是否出现过故障，建议汇总错误率和关键 API 告警。
- **数据库一致性**：本轮没有生产数据库只读巡检凭据，无法核实历史库中是否存在重复工资批次或银行流水、历史状态与实际转账是否一致。
- **全站交互验收**：登录角色矩阵、发票生命周期、合同审批、游戏渠道对账、手机端布局仍需有权限的浏览器端人工或自动 E2E 验收。
- **敏感附件访问**：账单附件使用私有 Blob 授权下载；同时代码保留旧的静态 `/uploads` 路由，需核查部署环境是否确有遗留文件并决定后续迁移清理，避免草率修改使已有下载失效。

## 上线后建议抽查

- 人工费用分别筛选某月与「全部月份」，确认应发/代扣/个税/实发汇总和工资批次总数一致。
- 用多个标签页同时导入同公司同月的测试工资表，确认只保留一笔，另一请求返回冲突。
- 运营费用 → 其他费用及押金，检查筛选切换迅速时不会出现上一月份的台账。
- 网络异常时显示错误和重试，不再显示错误月份的缓存金额。
